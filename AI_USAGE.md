# AI Usage — Ottodot Trial Booking

This file answers the take-home's six required questions directly below, then gives the full supporting evidence as a dated **Logs** section further down — written *while the work happened*, not reconstructed afterward. Every claim in the six answers links to a specific log entry rather than restating it, so the two sections stay in sync instead of drifting.

---

## 1. Which AI tools I used

**Claude Code (Sonnet 5)** — used interactively end-to-end: reading the brief, designing the data model and concurrency strategy, writing `TECH_DESIGN.md`/`openapi.yaml`/`README.md`, scaffolding and implementing the app, writing and running tests, and running verification tooling. No other AI tool was used at any stage.

## 2. What I used AI for

- **Scoping**: reading the take-home brief and turning it into a concrete set of invariants (duplicate bookings, overbooking, payment-failure isolation, the last-seat race) before any design started.
- **Design**: the data model, the auth/session model, and the two-step (optimistic pre-check + authoritative transaction) strategy for the last-seat race — written up in `TECH_DESIGN.md` with schema, transaction pseudocode, and five Mermaid sequence diagrams.
- **Implementation**: the entire Next.js/Prisma/SQLite app — schema + migrations, all API routes, the seed script, and a minimal UI — plus `openapi.yaml`, served via Swagger UI.
- **Testing**: a vitest integration suite that drives a real running server over real HTTP with real cookies (no mocks), including the required concurrent last-seat-race scenario.
- **Verification and fixing**: running `tsc`, `eslint`, `prisma migrate`, `next build`, `@redocly/cli lint`, and the test suite itself, then fixing whatever they found (see Q6).

Beyond the initial build, I directed the AI to add specific features on top of the working app, one prompt at a time rather than specifying everything upfront:

- **Login and register** — the app initially had no auth at all (every endpoint trusted a client-supplied `parentId`); I asked for accounts and directed the AI toward real sessions over a shortcut mock-login, and separately asked for registration and login to be two distinct steps rather than signup-with-auto-login.
- **Showing booking data for related parents** — a parent-facing "which classes/children are already booked and paid" view. Implemented as `GET /api/bookings` (scoped to the logged-in parent's own children only, same as everything else) plus a "My Bookings" page.
- **Cancellation, as a simpler alternative to deleting a booking outright** — rather than a destructive delete, cancellation flips `status` to `cancelled` with a required admin-supplied reason, preserving the row (and its payment history) instead of removing it. Allowed even on already-`confirmed`/paid bookings, which was the specific ask.
- **Adding a student for a registered/logged-in parent** — a gap the earlier work had left open: registration creates a parent account but zero children, and there was no way to add one, so a brand-new account could never actually book anything. `POST /api/students` plus a "My Children" page closed that.
- Smaller, iterative asks along the way: a general `Class`/`isTrial` model (assuming class data is owned by another system), a class `description`/`image`/`duration`, sequence diagrams of the user flow, and a Swagger/OpenAPI doc — each logged individually below.

## 3. One place AI helped me move faster

Designing the last-seat race fix in one pass instead of iterating manually over transaction-isolation semantics: working out that a **partial unique index** (`WHERE status = 'confirmed'`) closes the duplicate-booking case while a **live count-then-write inside one transaction** closes the capacity case, and writing both up immediately with concrete SQL/Prisma code, a full walkthrough with real numbers, and the Postgres equivalent (`SELECT ... FOR UPDATE`) — all in the first draft of `TECH_DESIGN.md` §5. Manually reasoning through SQLite-vs-Postgres locking semantics and writing correct transaction code for both would ordinarily take much longer than reviewing and correcting one.
→ *Log: "Writing `TECH_DESIGN.md`", 2026-07-26.*

## 4. One place I disagreed with, corrected, or rejected AI output

The first draft of `TECH_DESIGN.md` had every endpoint (`GET /api/students?parentId=`, etc.) trust a **client-supplied `parentId`** — meaning parent A could read parent B's children and bookings just by passing a different ID (an IDOR hole). I caught this myself after reading the draft, not because the AI flagged it, and rejected the "just document it as a cut" and "minimal mock session" options it offered in favor of implementing full accounts + sessions, prioritizing a correct access-control boundary over staying minimal.
→ *Log: "Caught a missing auth/authorization layer (user-flagged, not AI-flagged)", 2026-07-26.*

(A second, self-caught example is in the logs too: the AI's schema used Prisma `enum`s, which don't exist on SQLite — that one wasn't caught by review, it was caught by `prisma migrate dev` failing outright. See "Started implementation; caught a real schema bug immediately.")

## 5. What I'd change about my AI workflow next time

**Push the AI to execute or lint every design artifact during the design phase itself, before I review it — not after implementation starts.** Three separate bugs (the SQLite-incompatible `enum`s, two Mermaid diagrams that silently failed to render, and a Step-A capacity rule that would have made the brief's required race scenario unreachable) all existed as confident-sounding prose or diagrams that nobody had actually run, rendered, or traced with real numbers yet. Each was eventually caught, but later than it should have been — the enum bug in particular survived several rounds of my own review because I was reading the schema, not running it. If I did this again, I'd treat "I wrote a schema/diagram/spec" and "I ran it through a real tool" as two separate steps that both have to happen before calling a design artifact done, not one.

## 6. How I verified the final implementation

Two different kinds of verification happened, deliberately kept distinct:

**What I checked myself, hands-on:** I ran the app and used it directly — started the dev server, logged in with the seeded accounts, walked through booking/payment/cancellation, and opened `/api-docs` to check the Swagger UI against the actual running API rather than just trusting the YAML. This is the verification I'd point to first: does the thing actually work when a person drives it.

**What I gave to the AI to run, specifically to confirm the app was in a working state before I looked at it:**
- **Static checks**: `npx tsc --noEmit` and `npx eslint .` clean after every batch of changes, not just at the end.
- **Schema**: every migration actually applied via `npx prisma migrate dev`/`deploy` against real SQLite, including a from-scratch reset before the final pass.
- **API spec**: `npx @redocly/cli lint openapi.yaml` — validated as a real OpenAPI 3.0 document, not just checked for YAML syntax.
- **Build**: `npm run build` (production build, not just dev mode) succeeded.
- **Unit/integration tests**: `npm test` — 26 vitest tests against a real, freshly built production server (isolated build directory, so it can't collide with any dev server already running), driven over real HTTP with real cookies. Covers duplicate-booking rejection, non-trial rejection, overbooking rejection, payment-failure isolation, retry-after-failure, the full auth boundary, listing/detail endpoints, adding a child, admin cancellation with seat-reuse, and the required last-seat race fired as two genuinely concurrent HTTP payment requests. **Run repeatedly, not once** (10× after a harness fix, 4× after the cancellation feature, 3× after the add-a-student feature) — a real flake surfaced this way once already that a single green run would have hidden. See "'My Bookings' page ... and a real test-harness flake."
- The AI also ran its own curl-based cookie-jar walkthroughs of the full user journey against both dev and production builds, as a stand-in for browser testing it couldn't do itself (see the gap noted below).

The point of that split: the mechanical, repeatable checks (types, lint, migrations, build, tests) were delegated so they'd actually get run every time rather than skipped under time pressure, but they don't replace actually operating the app — that's the one thing I did myself before trusting the result.

**Known gap, stated rather than hidden**: no browser automation tool was available to the AI in this environment, so it could never visually verify rendered UI itself — only HTTP/JSON contracts and page-route status codes. My own manual run through the app and the Swagger UI is what actually covers that gap. Noted in `README.md` too.

### 2026-07-26 — Sequence diagrams surfaced a self-inconsistency in the race-condition design
- **Prompt summary:** User asked for the system's user flow as sequence diagrams.
- **What happened (self-caught, not user-flagged):** Writing the last-seat-race diagram forced a concrete walk-through with real numbers, which exposed that §5's Step A pre-check as originally written ("count `confirmed` + unexpired `pending_payment`") would have **blocked** the exact scenario the brief requires — if User A's pending hold counted against the 4-seat cap, User B could never even select the same slot, let alone reach payment. The earlier prose ("seat count was 1 confirmed + 0 pending → fine, or exactly at the edge") was hand-wavy precisely because the numbers didn't actually work out under that rule.
- **Fix:** Step A now counts **only `confirmed` bookings**, never pending ones — a `pending_payment` hold reserves nothing; only Step B's transactional check at payment time is authoritative. This is what makes two parents legitimately racing for the same last seat possible in the first place, which is the whole point of the required scenario. Updated §5 (rule + walkthrough, now using the actual seeded Class B numbers: 3 confirmed / 4 cap), §6 (payment-failure text no longer claims pending holds free up capacity), and §8 (background TTL sweep is now framed as housekeeping only, not a capacity fix).
- **Why this is worth recording:** it's a real example of a design bug that existed silently in prose (self-consistent-sounding but not diagrammed/traced with actual numbers) until being forced into a precise, step-by-step artifact. Good argument for producing the sequence diagram *before* implementation, not after. *(This example, together with the enum bug below, is the basis for the Q5 answer above.)*

### 2026-07-26 — Started implementation; caught a real schema bug immediately (self-caught, via the tool itself)
- **What happened:** User said the tech doc was complete and asked to implement it. Scaffolded Next.js + pinned Prisma to a stable 5.20.0 (the freshly-`prisma init`'d version was 7.9.0, bleeding-edge enough to use a different config format (`prisma.config.ts`) than anything documented in `TECH_DESIGN.md` — downgraded rather than rewrite the design around an unreleased-feeling toolchain). Reinforces the same lesson as the diagram fix: a design doc is a hypothesis until something actually executes it. *(This is the other half of the Q5 answer above.)*
